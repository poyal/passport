# 로컬 검증 후 배포하는 프로젝트 운영 안내

이 문서는 데스크톱 앱 등에서 수정할 때마다 원격 CI의 설치·빌드·패키징을 반복하는 비용을 줄이는 방법을 설명한다. 각 대상 OS에서 배포할 파일을 만들고 검사한 뒤, 그 파일을 다시 빌드하지 않고 게시한다. 다른 프로젝트에 적용할 원칙과 Passport의 실제 명령을 함께 정리했다.

## Windows 1.1.1 아이콘 수정본 교체 게시 완료 — 2026-10-03

사용자의 같은 버전 업데이트 요청으로 `v1.1.1-win-x64-icon-fix` 소스를 정식 로컬 검증하고 기존 Windows EXE를 교체했다. 소스/설치본 숨김 GUI는 각각 58개, 실제 데스크톱은 각각 4개 통과했고 작업표시줄의 Passport 아이콘과 공개 다운로드 해시도 확인했다. 기존 Mac 파일·태그와 최초 Windows 소스 태그는 보존했다. 이전 EXE는 공개 바이트로 백업하고 새 파일을 미리 업로드·다운로드 검증한 뒤 공개 이름을 승격했다. 이번 작업에서 원격 Actions를 실행하지 않았다. [아이콘 수정 게시 요약](benchmarks/github-release-windows-v1.1.1-icon-fix.json)과 [검증 기록](verification.md)을 따른다.

## Windows 1.1.1 x64 로컬 배포 완료 — 2026-10-03

소스·최종 설치본의 숨김 GUI는 각각 58개 통과·허용 생략 4개, 데스크톱 검사는 각각 4개 통과했다. Windows 입력 버그픽스를 `v1.1.1-win-x64` 소스로 검증하고 기존 릴리즈에 재빌드 없이 게시했다. Mac 파일과 기존 태그는 보존했다. 이번 미게시 Windows 버전의 변경은 사용자가 승인했으며 아래의 제한된 소스 예외를 따른다. 상세 해시·실패 기록·검증 범위는 [Windows 게시 요약](benchmarks/github-release-windows-v1.1.1.json)과 [검증 기록](verification.md)에 있다.

## 1.1.1 Mac 로컬 배포 완료 — 2026-10-02

소스 `f4497cc2a337c5f5aa73d5834a2b99f06013020d`의 Mac DMG를 정식 로컬 절차로 검증한 뒤 동일 바이트로 게시했다. 단위·통합 131개, 배포 회귀 61개, 소스/최종 DMG의 숨김 GUI 각 53개와 실제 포커스 각 4개를 통과했다. 허용 생략은 단위 3개와 GUI 각 9개이며 최종 실패·재시도는 없다. 공개 파일 다운로드 해시도 확인했다. 사용자 Finder 전체 경로·이미지 첨부 표시도 확인했으며 Windows 실기·배포는 별도다.

`release/builds/Passport.app`은 검증한 1.1.1 앱을 가리킨다. Mac은 Playwright 기본 정상 종료 뒤 실제 프로세스 종료를 확인하며 Windows는 기존 종료 순서를 유지한다. 초기 실패·검사 보완·검증 범위는 저장소 `docs/verification.md`와 `docs/benchmarks/github-release-v1.1.1.json`에 기록했다. README 작성 규칙은 `docs/README-작성-가이드.md`와 `AGENTS.md`에 연결했다.

기존 Mac/Windows 게시 Actions를 비활성화하고 수동 진단만 남겼다. 초기 Windows 1.1.1은 사용자 승인에 따라 버그픽스 소스 태그 `v1.1.1-win-x64`를 사용했다. 아래는 앞선 개발 단계별 기록이며 당시 미완료 항목을 현재 상태와 혼동하지 않는다.

## Finder 전체 경로 후속 수정 — 2026-10-02

실제 Finder 복사에서 앱 이름만 입력된다는 사용자 재현을 반영해 macOS AppKit의 파일 URL 목록을 직접 읽도록 수정했다. 파일·폴더·앱 및 다중 선택의 절대경로를 전달한다. 별도 macOS pasteboard로 실제 URL을 읽는 회귀를 추가했고 단위 **19개**, 개발/최종 앱의 붙여넣기 GUI **각 3개**, 배포 회귀 **60개**, 패키지 실제 PTY/종료 검사를 통과했다. 필수 GUI 목록은 현재 **숨김 62개·데스크톱 4개**이며 새 Mac 전용 검사 1개는 Windows에서 플랫폼 사유로 생략한다.

수정된 미리보기는 저장소 `release/builds/Passport.app`에서 연다. 기존 Passport를 ⌘Q로 종료한 뒤 사용한다. 사용자의 일반 클립보드를 바꾸지 않고 검사했으므로 Finder에서 직접 복사·붙여넣기는 사용자 재확인이 필요하다. Windows 실기·릴리즈는 사용자가 진행한다. 자세한 출처·해시는 `docs/benchmarks/finder-paths-20261002.json`과 `docs/verification.md`에 남겼다.

## 파일·이미지 붙여넣기와 Windows 인계 — 2026-10-02

Mac·Windows 파일·이미지 붙여넣기 구현과 회귀 검사를 추가했다. 현재 필수 GUI 목록은 **숨김 61개·데스크톱 4개**다. Mac에서 격리된 zsh 설정으로 **단위·통합 129개 통과·3개 생략**, **숨김 GUI 52개 통과·허용 생략 9개**, **배포 회귀 60개 통과**를 확인했다. 개인 로그인 셸을 읽는 초기 검사에서는 기존 PTY/GUI 시작 제한 시간 초과가 있었고, 그 실패 기록과 격리 환경 조건을 `docs/verification.md`에 남겼다.

Windows 실기 검증과 릴리즈는 사용자가 집의 Windows PC에서 진행한다. 저장소의 `docs/windows-paste-release.md`에 네 가지 셸·탐색기·Claude/Codex 수동 확인과 정식 검증·게시 명령을 정리했다. Finder/탐색기의 실제 복사 및 CLI 이미지 해석 성공은 아직 확인하지 않았다. 이번 결과는 개발 빌드의 범위별 검증이며 새 설치본이나 게시 가능한 기록은 아니다. 장기 요약은 `docs/benchmarks/clipboard-paste-20261002.json`에 있다.

## 터미널 기능 추가에 따른 검증 목록 갱신 — 2026-10-02

터미널별 자동 읽음 처리, 현재 창/새 창의 로컬 터미널 단축키, OS 설치 폰트와 내장 글꼴 7종을 추가했다. 필수 GUI 목록은 **숨김 59개·데스크톱 4개**로 갱신했다. Mac 숨김 전체는 **50개 통과·허용 생략 9개**, 타입·단위/통합은 **123개 통과·3개 생략**, 배포 회귀는 **60개 통과**했다. 이번에도 네이티브 창 표시·포커스 획득을 차단했다.

알림의 숨김 통합 시험은 창 상태 조회만 대체하고 실제 IPC·DB를 사용한다. 실제 OS 포커스·알림 센터 동작과 Windows 실기 검증은 별도로 남긴다. 새 최종 설치본이나 게시 가능한 기록은 만들지 않았다. 상세 기록은 `docs/benchmarks/terminal-experience-20261002.json`에 보관한다. 아래 앞선 검증 수치는 각 단계 당시의 기록이다.

## 페리로그 검토 반영 — 2026-10-02 후속 보강

페리로그의 운영 가이드와 전달용 검토안을 대조해 필수 GUI 검사 누락 차단, Actions 전환 확인, 잠금 범위와 프로젝트별 확장 기준을 보강했다. 개발 중에는 관련 검사만 반복하고 후보 확정 후 전체 로컬 검증을 수행한다. 같은 후보의 원격 전체 검사나 게시 전 재빌드를 추가하지 않는다.

배포 회귀 **60개 통과**, 창을 실행하지 않는 테스트 목록 대조 **숨김 56개·데스크톱 3개**를 확인했다. 앞서 저장한 Mac 숨김 GUI 보고서도 새 정책에 대조해 **필수 47개 통과·허용 생략 9개**를 확인했다. 이것은 기존 보고서 재판정이며 GUI·최종 설치본·Windows를 새로 실행한 결과가 아니다. 검증 기록 형식을 3으로 올렸으므로 이전 형식의 기록은 게시에 재사용할 수 없다.

원격 읽기 전용 조회에서 Mac 게시 `370814382`, Windows 게시 `371212218`, Desktop 검사 `369898876`은 모두 `active`였고 실행·대기 작업은 0개였다. 이번 작업은 원격 워크플로 상태·태그·공개 파일을 변경하지 않았다. 전환 완료 조건과 명령은 아래 「Actions 운영」에 있으며 상세 근거는 `docs/benchmarks/release-hardening-20261002.json`에 보관한다.

## E2E 작업 방해 개선 — 2026-10-02 후속 갱신

일반 E2E의 기본 실행을 숨김 모드로 전환했다. `npm run test:e2e:show`는 창만 표시하고 포커스는 가져오지 않으며, OS 포커스·클립보드 검사 3개는 `npm run test:e2e:desktop`으로 분리했다. 기본 검사에서 해당 항목을 제외한 사실을 배포 기록에서도 구분하며, 정식 배포에는 별도 데스크톱 검사 통과가 여전히 필요하다.

Mac ARM64에서 숨김 E2E **47개 통과·9개 조건부 생략**, 창만 표시하는 시나리오 **1개 통과**를 확인했다. 숨김 시나리오의 내부 창 2개는 표시·네이티브 포커스 모두 0회였고, 표시 모드의 창 2개도 포커스 획득 0회였다. 모든 실행된 숨김 앱의 종료 검사에서도 표시·포커스 횟수 0을 확인했다. Windows 전용·선택 부하 9개는 생략됐으며, 전경 검사 3개는 이번 실행에 포함하지 않았다. 빌드·타입, 창 정책 단위 2개와 최종 배포·중단 보호 회귀 36개도 통과했다.

테스트 앱 잔여 프로세스는 없고 사용자 Passport 실행본은 유지했다. Windows의 새 숨김 모드와 새 최종 설치본은 이번에 검증하지 않았다. 아래 초기 전경 검사에서 발생한 종료 문제의 근본 원인을 확정한 것도 아니다. 상세 후속 기록은 `docs/benchmarks/background-e2e-20261002.json`에 보관한다.

## 초기 배포 전환 검증 — 2026-10-02

Passport에는 `release:check`, `release:verify`, `release:publish`와 수동 진단용 Actions 전환을 로컬 코드로 구현했다. **전환 로직과 실패 시 차단은 확인했으나 전체 배포 검증을 통과한 상태는 아니다.** 아래는 `2c60496` 위의 미커밋 변경을 검사한 결과이며 다른 프로젝트의 성공을 보장하는 결과가 아니다.

테스트 Electron의 간헐적인 종료 지연으로 응답 없음 알림이 발생했다. 정상 종료에 10초 제한을 두고 시험 소유 프로세스만 정리하도록 보완했으며, 제한 초과나 강제 종료는 실패로 처리해 패키징·게시를 차단한다. 사용자 실행본과 데이터는 유지했다. **종료 지연의 근본 원인은 미확정**이며, 마지막 관련 GUI 14개 통과를 전체 문제 해결로 간주하지 않는다.

새 방식으로 실제 배포하려면 종료 문제를 해결하고 Mac 최종 DMG 페이로드와 Windows 각 아키텍처의 전체 검증을 통과해야 한다. 이번 작업은 새 DMG·EXE나 게시 가능한 검증 기록을 만들지 않았다. 전환 변경도 아직 push하지 않았으므로 원격 Actions 운영은 기존 상태다.

상세 기록은 Passport 저장소의 `docs/verification.md`와 `docs/benchmarks/local-release-20261002.json`에 있다. 이 절의 결과는 위 날짜의 검증 범위이며, 아래 운영 절차의 모든 단계가 이미 성공했다는 의미가 아니다.

## 검증과 게시의 경계

### 미게시 Windows 1.1.1의 소스 예외

2026-10-02 사용자가 Windows 1.1.1의 테스트 보정과 버그픽스를 같은 버전으로 배포하도록 승인했다. 기존 Mac의 `v1.1.1` 태그(`f4497cc`)와 DMG는 보존하고, Windows 검증 소스에는 별도 `v1.1.1-win-x64` 태그를 붙인다. 게시 도구는 이 버전·플랫폼에만 예외를 적용하며 기존 Mac 태그·파일 ID·크기·해시와 새 소스 태그를 확인한다. 소스는 기존 태그의 후속 커밋이어야 하고, 앱 변경은 Windows Bash 입력 보정 두 파일과 [공식 ConPTY 동시 접근 수정](https://github.com/microsoft/node-pty/pull/922)의 컴파일·배치로 제한하며 테스트·검증 스크립트·문서 변경 목록도 기계적으로 확인한다. ConPTY 패치는 원본·수정 소스 해시를 확인하고 해당 아키텍처의 로더 대체 경로에도 컴파일한 모듈을 배치한다.

깨끗한 현재 소스와 검증 기록의 커밋·지문 일치, 모든 필수 검사, 설치본·증거 해시, 다운로드 재검증은 그대로 적용한다. 실패 기록이나 다른 Windows 파일을 덮어쓰는 예외는 없다. 이후 릴리즈와 다른 플랫폼은 기존 동일 태그·소스 계약을 따른다.

### 사용자 요청에 따른 Windows 1.1.1 아이콘 수정본 교체

2026-10-03 사용자가 이미 게시한 Windows 1.1.1의 Electron 기본 아이콘 문제를 수정하고 같은 버전의 설치 파일을 갱신하도록 명시적으로 요청했다. 이 요청에는 기존 Windows EXE 교체가 포함되므로 위의 최초 게시 규칙과 구분한다. `--replace-windows-icon`은 Windows x64 1.1.1에만 적용한다. 기존 Windows 파일의 ID·크기·SHA-256과 `v1.1.1-win-x64` 커밋을 고정하고, 새 후보에는 `v1.1.1-win-x64-icon-fix` 태그를 사용한다. 기존 태그는 이동하지 않는다.

전체 검증 기록을 다시 확인하고 새 파일을 임시 자산으로 업로드·다운로드 검증한 뒤 기존 이름으로 교체한다. 기존 공개 파일은 `release/packages/v1.1.1/github/win-x64/`에 해시와 출처를 남겨 보관한다. 수정본의 로컬 보관 위치는 `release/packages/v1.1.1/local/win-x64/icon-fix-<커밋>/`다. Mac 파일은 보존하고 합본 체크섬을 갱신한다. 기본 게시 명령의 다른 바이트 덮어쓰기 거부와 실패·재시도·증거 해시 검사는 유지한다. 교체 뒤 같은 버전의 새 버전 알림은 없으므로 사용자는 EXE를 다시 내려받아 설치한다.

```powershell
npm.cmd run release:publish -- --manifest release/checks/<실행 ID>/verification.json --replace-windows-icon
npm.cmd run release:publish -- --manifest release/checks/<실행 ID>/verification.json --replace-windows-icon --execute
```

개발 중에는 빠른 검사와 실패한 시나리오를 반복한다. 배포 후보가 정해지면 전체 검사를 한 번 수행한다. 게시 명령은 통과한 검증 기록과 설치본을 입력으로 받으며 빌드를 실행하지 않는다.

```text
코드 수정 → 타입·단위 검사 → 필요한 GUI 검사
                                 ↓
                       배포 커밋 확정
                                 ↓
            해당 OS에서 잠금 파일로 의존성 설치
                                 ↓
             빌드 → 전체 소스 검사 → 설치본 생성
                                 ↓
                설치본 내용·실행·종료 검사
                                 ↓
             커밋·설치본 해시·검사 결과 기록
                                 ↓
               게시 계획 확인 → 동일 파일 게시
```

Mac 검증은 Mac에서, Windows 검증은 Windows에서 수행한다. 한 OS의 통과 기록으로 다른 OS나 아키텍처의 검증을 대신하지 않는다. 로컬과 원격의 환경 차이로 발견한 문제는 고정된 회귀 검사로 남긴다. 긴 PATH, 권한이 제한된 파일, 셸 준비 시점, 조용한 터미널의 종료가 그 예다.

## 다른 프로젝트에 적용할 계약

다음 세 명령을 프로젝트의 언어와 빌드 도구에 맞춰 구현한다. 아래 이름은 Passport가 사용하는 이름이며 다른 프로젝트에서는 대응하는 명령을 만들면 된다.

| 명령              | 책임                                                          | 원격 변경                           |
| ----------------- | ------------------------------------------------------------- | ----------------------------------- |
| `release:check`   | 타입·단위 검사와 배포 스크립트 검사                           | 없음                                |
| `release:verify`  | 대상 OS에서 빌드·전체 검사·패키징·최종 파일 검사 후 기록 생성 | 없음                                |
| `release:publish` | 기록과 파일을 다시 확인하고 동일 파일 게시                    | 기본은 조회만, `--execute`에서 게시 |

검증 기록에는 저장소, 버전, 커밋, 작업 폴더 변경 여부와 변경 파일 목록, 소스 지문, OS·아키텍처, 도구 버전, 실행한 검사와 생략 범위, 설치 파일의 경로·크기·SHA-256, 로그·보고서 해시를 넣는다. 성공 기록은 모든 필수 단계가 끝난 뒤에만 생성한다. 실패나 중단 기록을 성공으로 바꾸는 수동 우회 옵션은 만들지 않는다.

검사 로그 파일을 만들 수 있는지 확인한 뒤 작업을 시작한다. 기존 로그와 경로가 충돌하면 덮어쓰거나 백그라운드 빌드를 남기지 않고 실행 전에 중단한다.

게시 전에는 현재 소스와 기록의 커밋·지문이 같은지, 설치 파일과 증거 파일이 바뀌지 않았는지, 원격 태그가 해당 커밋을 가리키는지 검사한다. 검증한 파일을 메모리나 변경 불가능한 스냅샷에 고정한 뒤 업로드하고, 다시 내려받은 해시까지 확인한다. 같은 파일명이나 버전은 같은 빌드라는 증거가 아니다.

Passport의 `release:verify`와 `release:publish`는 **동일 작업 폴더**의 `release/checks/local-release.lock`으로 직렬화한다. 일반 개발 빌드나 같은 컴퓨터의 다른 clone/worktree, 다른 컴퓨터에는 이 잠금이 적용되지 않는다. 버전별 게시 담당자·세션과 작업 폴더를 하나로 정하거나, 각 OS의 검증 자료를 한 게시 작업으로 모은다. 원격 자산 재조회는 분산 잠금이나 원자적 갱신을 대신하지 않는다. 공유 체크섬 갱신 중 업로드가 끊겨도 기존 설치본을 지우지 않고 다시 실행해 복구해야 한다.

잠금 파일에는 호스트명·PID·작업 폴더·시작 시각을 남긴다. 비정상 종료로 파일이 남으면 해당 호스트의 소유 프로세스와 자식 작업이 끝났는지 확인한 뒤 해제한다. 오래된 파일이라는 이유로 자동 삭제하지 않는다.

## 환경 재현

의존성 잠금 파일을 커밋하고 배포 검증은 깨끗한 의존성 설치로 시작한다. 도구 버전은 팀에서 정한 버전으로 맞추고 검증 기록에도 남긴다. 네이티브 모듈은 OS·아키텍처·런타임 ABI·컴파일러가 같은 결과만 재사용한다. 캐시가 있다는 이유만으로 다른 환경의 바이너리를 사용하지 않는다.

깨끗한 배포 후보와 평소 개발 폴더를 구분하면 캐시에 가려진 문제를 줄일 수 있다. 로컬 검증이 모든 사용자 환경의 성공을 보장하지는 않는다. 필요할 때 깨끗한 CI 또는 별도 기기에서 같은 검증 명령을 실행해 환경 의존성을 확인한다.

파일 게시 권한은 게시 단계에서만 필요하다. 토큰을 검증 기록·로그·저장소에 쓰지 않는다. 로컬 JSON 기록은 실수를 막는 장치이며 암호학적 서명이나 독립된 공급망 증명을 대신하지 않는다.

## Passport 사용법

Node.js 24 이상, npm, Rust cargo, macOS의 Xcode Command Line Tools 또는 Windows의 MSVC C++ 빌드 도구와 Spectre 완화 라이브러리를 준비한다. Windows는 Python·OpenSSL·Windows PowerShell·PowerShell 7이 필요하다. `openssl`이 PATH에 없으면 Git for Windows의 `usr/bin`을 추가한다. Mac은 Python 3과 OpenSSL이 필요하다. `PASSPORT_CARGO`로 cargo 위치를 지정할 수 있다.

`npm ci`를 수행하는 배포 검증은 Electron용 네이티브 의존성과 Rust helper를 새로 준비한다. FTP/FTPS용 Python 가상 환경은 해당 검증 폴더에 만들며, 준비된 별도 Python이 있으면 `FTP_TEST_PYTHON`을 지정할 수 있다. Cargo는 프로젝트가 지정한 MSVC 또는 Apple Silicon 대상을 사용한다. 실행된 Node·npm·cargo·Electron 버전은 기록된다. 현재 스크립트는 Node의 최소 버전을 검사하며 Node·Rust의 패치 버전까지 강제하지는 않는다.

개발 중 빠른 확인:

```sh
npm run release:check
# 예: Windows에서 종료와 셸 문제를 수정할 때
npx playwright test tests/e2e/windows-shells.spec.ts tests/e2e/shutdown.spec.ts
```

소스 GUI 검사는 먼저 `npm run build`가 필요하다. Windows는 `npm run prepare:runtime -- x64` 또는 `arm64`로 내장 Bash도 준비한다.

다른 작업 중에도 실행할 수 있는 숨김 모드 리허설:

```sh
npm run release:verify -- --preview
```

`--preview`는 커밋하지 않은 변경도 검사하며, 기본적으로 창을 숨기고 OS 포커스 검사를 제외한다. 모든 실행 단계가 통과하면 결과는 `preview-verified`지만 게시할 수 없다. `--preview --desktop`을 명시하면 OS 포커스 검사도 포함하므로 작업을 분리한 데스크톱에서 실행한다. 실패를 고친 뒤에는 관련 검사로 먼저 확인하고 전체 검증을 다시 수행한다.

정식 배포 후보는 버전·릴리즈 노트·모든 변경을 커밋한 뒤 검사한다:

```sh
npm run release:verify -- --desktop
```

명령은 `release/checks/<실행 ID>/verification.json`을 출력한다. 일반 GUI는 숨김 모드로, 네이티브 포커스·클립보드 검사는 별도로 실행한다. 정식 검증에서 `--desktop`을 생략하면 작업 시작 전에 거부하며, 게시 기록에도 소스와 최종 패키지 양쪽의 데스크톱 검사 통과가 필요하다. Mac에서는 최종 DMG를 읽기 전용으로 마운트해 서명 무결성·실제 PTY·전체 GUI·정상 종료를 검사한다. Windows에서는 NSIS의 현재 사용자 범위와 `/allusers` 거절을 확인하고, EXE에 포함된 페이로드를 추출해 실제 PTY·전체 GUI·정상 종료를 검사한다.

검증 후 동일한 커밋과 태그를 원격에 올린다. 태그는 `v<package.json 버전>`이어야 한다. 게시 명령은 소스 push나 태그 생성·이동을 자동으로 하지 않는다. 이미 공개한 버전을 다른 빌드로 바꾸려면 새 버전을 사용한다. 기존 1.1.0의 Mac·Windows 소스가 서로 달랐던 과거 배포는 그대로 보존하며 새 방식의 동일 커밋 규칙을 소급 적용하지 않는다.

```sh
# 조회만 수행하며 게시할 내용과 보존할 파일을 보여 준다.
npm run release:publish -- --manifest release/checks/<실행 ID>/verification.json

# 계획을 확인한 뒤 동일 파일을 게시한다.
# gh auth login 또는 GH_TOKEN 인증이 필요하다.
npm run release:publish -- --manifest release/checks/<실행 ID>/verification.json --execute
```

여러 플랫폼의 설치본은 같은 커밋에서 검증한다. 한 컴퓨터에서 함께 게시하려면 각 컴퓨터의 `release/builds/<실행 ID>`와 `release/checks/<실행 ID>`를 상대 경로 그대로 복사하고 `--manifest`를 여러 번 지정한다. 또는 각 OS에서 차례로 게시한다. 게시 명령은 기존 플랫폼 파일과 체크섬을 확인·보존한다. GitHub의 불변 릴리즈 설정이 켜져 있다면 모든 플랫폼을 한 번에 게시해야 한다.

새 릴리즈는 초안으로 만든 뒤 파일 업로드와 다운로드 검증이 끝나야 공개한다. 중간에 실패하면 같은 명령을 재실행한다. 이미 올라간 동일 파일은 보존하며 누락된 파일과 합본 체크섬을 복구한다. 다른 내용의 같은 이름 파일은 덮어쓰지 않는다. 기존 공개 릴리즈에 플랫폼을 추가할 때는 체크섬 교체 중 잠깐 파일이 없을 수 있으므로 동시 게시하지 않는다.

`release:publish --execute`는 실제 외부 게시 명령이다. 작업 요청에 게시가 포함되지 않았다면 검증과 계획 확인까지만 수행한다.

## 자동 검사 범위와 별도 확인

### 다른 작업을 방해하지 않는 GUI 검사

```sh
npm run test:e2e                           # 기본: 창 숨김, OS 포커스 없음
npm run test:e2e:show                      # 창은 표시하되 포커스 없음
npm run test:e2e:desktop                   # 실제 OS 포커스·클립보드 검사만
npm run test:e2e -- tests/e2e/shutdown.spec.ts
```

이미 빌드했다면 `node scripts/e2e.mjs <검사 파일>`로 필요한 검사만 반복한다. 결과는 `release/checks/<실행 ID>/`에 기록한다. `npx playwright test`도 기본 숨김 모드이며, `PASSPORT_E2E_MODE`는 `hidden`, `passive`, `desktop`을 지원한다.

일반 검사는 앱 생성 시점부터 `show: false`, `focusable: false`를 적용해 창 깜박임과 포커스 이동을 막는다. 창만 표시하는 모드는 `showInactive()`를 사용하며 추가 창·알림 열기·두 번째 인스턴스 요청에도 같은 정책을 적용한다. Playwright의 렌더러 입력과 스크린샷은 계속 검사하지만 이것을 네이티브 OS 포커스 검증으로 보지 않는다. OS 포커스·클립보드 검사는 `@desktop`으로 분리해 명시적으로 요청할 때만 실행한다. 정상 사용자 앱은 이 테스트 설정을 사용하지 않는다.

예전 설치본이 숨김 모드를 지원하지 않으면 창을 띄우기 전에 거부한다. 먼저 새 소스로 빌드해야 하며, 테스트를 통과시키기 위해 자동으로 전경 실행으로 전환하지 않는다. 숨김 모드에서도 Electron용 데스크톱 세션은 필요하다. 다른 프로젝트도 창 생성 정책을 공통으로 적용하고, 숨김 검사와 실제 OS 상호작용 검사 결과를 구분한다.

### 배포 검증 범위

자동 검증은 단위·프로토콜 검사, 전체 소스 GUI, 설치본 생성, 설치본에서 읽은 앱의 GUI·네이티브 PTY·종료를 포함한다. FTP/FTPS fixture는 필수이며 준비에 실패하면 배포 검증도 실패한다. GUI 보고서는 실행 수·실패·생략 수를 기록하고, 재시도와 flaky 결과를 허용하지 않는다. 첫 실패에서 해당 GUI 단계를 중단한다. 시험 앱의 정상 종료에는 10초 제한을 두며, 넘으면 시험 소유 프로세스 트리만 종료하고 실패로 기록한다.

`tests/e2e/release-policy.json`에 안정적인 ID, 파일·테스트 이름, 모드, 대상 플랫폼과 허용 생략 조건을 명시한다. 소스와 최종 패키지 각각 실행 전에 Playwright 목록을 대조하고, 실행 후에는 원본 보고서의 개별 결과를 검사한다. 필수 테스트의 생략·누락·이름 변경·결과 없음·중단·예상 실패 처리와 중복은 실패다. 총 개수나 성공 1개만으로 전체 통과로 판정하지 않는다. 목록은 실행 때 자동 생성하지 않으며 테스트 변경과 함께 검토해 갱신한다. 이름을 바꿔도 기존 ID는 유지한다.

현재 숨김 목록은 62개, 별도 데스크톱 목록은 4개다. Mac에서는 Windows 전용 6개만 플랫폼 사유로 생략할 수 있다. Docker·장시간 스트레스·대용량 텍스트 3개는 선택하지 않았을 때만 생략할 수 있다. 각각 `PASSPORT_DOCKER_MANIFEST`, `PASSPORT_UI_STRESS=1`, `PASSPORT_TEXT_BENCH=1`을 지정하면 통과가 필수다. Windows의 내장 Bash·cmd·Windows PowerShell·PowerShell 7과 DPAPI·드라이브 검사는 필수이며 환경 미준비로 생략되어도 릴리즈 검증은 실패한다.

검증 기록에는 정책 해시와 테스트 ID별 결과·필수 여부·허용 생략 사유를 저장한다. 게시 시에도 해시를 확인한 소스·패키지 원본 보고서 4개를 같은 정책으로 다시 판정한다. 기록의 `status`나 집계 숫자만 바꾸어 검사를 대신할 수 없다. 새 정책을 통과한 형식 3 기록이 필요하며 이전 기록의 형식 번호만 고쳐 재사용하지 않는다.

Windows의 실제 사용자 계정 설치·제거·업그레이드, 물리 한글 IME, OS 알림, 실제 AI 서비스, 선택 Docker·장시간 부하는 별도 기기 검증이다. 패키지 실행 성공을 이 항목들의 성공으로 기록하지 않는다. 실제 설치 시험은 기존 앱·레지스트리를 바꿀 수 있으므로 격리된 사용자나 VM을 사용한다.

현재 Mac 빌드는 ad-hoc 서명이다. 서명 무결성 검사는 Developer ID 서명·공증·Gatekeeper 승인과 다르다. 정식 서명으로 전환할 때에는 검증 파이프라인의 패키징 단계에도 해당 설정을 적용한다.

## Actions 운영

Passport는 태그 push 게시 워크플로와 Windows 원격 게시 워크플로를 제거하고 2026-10-02 원격에서도 명시적으로 비활성화했다. `Desktop verification (manual diagnostics)`만 남겨 필요할 때 전용 runner에서 같은 `release:verify -- --desktop`을 실행한다. 이 워크플로는 저장소 읽기 권한만 가지며 공개 릴리즈를 게시하지 않는다. 다른 프로젝트에서도 검증 명령을 공통으로 만들고 CI 전용 검사를 따로 복제하지 않는 편이 유지보수에 유리하다. 페리로그처럼 검증된 파일만 업로드하는 가벼운 게시 Actions는 프로젝트 정책에 따라 유지할 수 있다.

**기본 브랜치의 YAML 삭제만으로 과거 ref의 자동 게시까지 차단되지 않는다.** 태그 push는 해당 커밋/ref의 워크플로를 사용한다. 자동 게시를 중단하는 전환에서는 기존 게시 워크플로를 명시적으로 비활성화하고 상태를 재조회한다. 이미 실행·대기 중인 작업도 확인·처리한 뒤 변경한 워크플로를 원격에 반영한다. 태그를 push하기 전에 그 대상 커밋의 실제 워크플로에도 전환이 포함됐는지 확인한다. [GitHub 워크플로 선택 기준](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows#workflow-triggers) · [비활성화 방법](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows).

GitHub CLI를 설치·인증한 환경에서 다음과 같이 전환한다. 비활성화는 원격 설정 변경이므로 실제 전환 작업 때 수행한다. Passport는 아래 순서로 실제 전환했으며 비활성화 시에는 조회한 워크플로 ID를 사용했다.

```sh
# 먼저 이름·ID·상태를 확인한다.
gh api --paginate repos/poyal/passport/actions/workflows --jq '.workflows[] | [.id,.name,.path,.state] | @tsv'
# 확인한 기존 게시 워크플로만 비활성화한다.
gh workflow disable release.yml --repo poyal/passport
gh workflow disable release-windows.yml --repo poyal/passport
# 위 조회를 반복해 disabled_manually 상태를 기록한다.

# 실행·대기 상태별 모든 페이지를 조회한다(Bash/zsh 예시).
for run_status in queued in_progress waiting pending requested; do
  gh api --paginate "repos/poyal/passport/actions/runs?status=$run_status&per_page=100" --jq '.workflow_runs[] | [.id,.name,.head_sha,.status,.html_url] | @tsv'
done

# 로컬 릴리즈 태그를 만든 뒤 push 전에 대상 YAML을 직접 검토한다.
git ls-tree -r 'v<버전>' -- .github/workflows
git show 'v<버전>:.github/workflows/desktop.yml'
```

실행 중인 게시 작업이 있으면 담당자와 소유 실행 ID를 확인해 완료 또는 취소 결과를 남긴다. 비활성화 자체가 기존 실행을 취소하지는 않는다. 삭제된 워크플로 조회 실패나 목록에서 안 보이는 것만으로 비활성화를 입증하지 않는다. ID·최종 상태·진행 중 작업·태그 커밋과 확인 시각을 기록한다. 확인 목적으로 과거 커밋에 시험 태그를 원격 push하지 않는다.

## 산출물과 보관

- `release/builds/<실행 ID>/`: 만든 앱과 DMG·EXE.
- `release/checks/<실행 ID>/`: 검증 기록·로그·GUI trace·임시 추출 파일.
- `release/packages/v<버전>/local/<플랫폼>/`: 게시된 로컬 설치본과 게시 결과.
- `release/backups/`: 사용자가 요청한 설치 교체를 위한 복구 세트.

실행 폴더에는 커밋·플랫폼·출처·검증 상태를 기록한다. Mac 미리보기 링크 `release/builds/Passport.app`은 검증된 빌드만 가리킨다. 설치본·로그·사용자 DB를 Git에 넣지 않는다. 다른 프로젝트에도 같은 분류를 적용하되 기존 보관·복구 규칙을 우선한다. 실패 재현 자료, 실행 중인 앱, 링크 대상과 복구 백업은 임의로 정리하지 않는다.

## 도입 검증 목록

정상 배포 외에도 검증 실패, 커밋 변경, 같은 크기의 설치본 변경, 로그 변경, 다른 원격 태그, 같은 이름의 다른 파일, 업로드 중단, 체크섬 업로드 실패, 재실행, 기존 플랫폼 파일 보존을 확인한다. 실제 GitHub 게시 전에는 원격 API를 대체한 테스트로 변경 순서와 복구를 검사하고, 해당 OS에서 실제 최종 파일의 실행을 따로 확인한다.

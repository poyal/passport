# SSH 호스트 키 변경 화면 벤치마크

2026-09-30. 첨부한 Termius 화면과 Passport 0.3.2 코드를 비교한 제안이다. [인터랙션 시안](../design/ssh-host-key-preview.html)은 예시 데이터로 동작하며 실제 자산·키·연결을 변경하지 않는다.

## 권장 방향

SSH 호스트 키가 바뀌면 연결 탭 안에 복구 화면을 표시한다. 서버 주소, 연결 단계, 이전 지문과 새 지문, 선택 결과를 한 화면에 보여준다. 사용자는 같은 자산의 키를 교체할지, 해당 주소를 사용하는 새 자산을 등록할지 결정한다.

첫 연결 확인을 끄는 기존 설정은 유지한다. 이미 등록한 키가 달라졌을 때는 이 화면으로 전환하고, 선택이 완료되기 전까지 사용자 인증을 진행하지 않는다. SSH·SFTP·터널 모두 같은 확인 결과를 사용해야 한다.

## Termius에서 가져올 점

| 관찰 항목 | 첨부한 Termius 화면           | Passport 제안                                                      |
| --------- | ----------------------------- | ------------------------------------------------------------------ |
| 표시 위치 | 해당 연결 탭 안의 화면        | 해당 연결 패널에 표시. 다른 세션은 계속 사용할 수 있음             |
| 진행 상태 | 연결 → 지문 → 터미널          | 서버 연결 → 호스트 키 → 사용자 인증 → 터미널                       |
| 변경 설명 | 저장된 지문이 바뀌었음을 알림 | 변경 사실을 먼저 설명하고 재설치·키 재발급·서버 교체 가능성을 안내 |
| 비교 정보 | 새 ECDSA 지문 표시            | 이전/새 지문, 키 종류, 마지막 확인 시각, 복사 기능                 |
| 조치      | Replace / Add as new / Cancel | 기존 자산의 키 교체 / 신규 자산으로 등록 / 연결 취소               |
| 판단 근거 | 연결 로그 버튼                | 비밀정보를 제외한 연결 단계 로그와 지문 확인 방법                  |

첨부 화면만으로 Termius의 **Add as new가 새 자산을 만드는지, 알려진 키를 추가하는지**는 확인할 수 없다. 검토한 [공식 연결 안내](https://docs.termius.com/organize-and-connect-to-hosts/connecting-to-a-server)와 [문제 해결 안내](https://docs.termius.com/help-center/troubleshooting/i-cant-connect-to-a-host)에도 이 버튼의 저장 동작은 설명되어 있지 않았다. Passport의 버튼 이름과 저장 동작은 아래처럼 명확히 정의한다.

## 교체와 신규 등록의 차이

| 선택                | 적합한 상황                             | 유지하는 것                                           | 바꾸는 것                                                                              |
| ------------------- | --------------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 기존 자산의 키 교체 | 같은 서버의 OS 재설치, 호스트 키 재발급 | 자산 ID·이름·그룹·인증 연결·설정·로그 소속            | 확인한 키를 활성 키로 바꾸고 이전 키·변경 시각을 이력으로 보관                         |
| 신규 자산으로 등록  | 같은 IP/포트에 다른 서버 배치           | 이전 자산과 로그를 이력으로 보관. 새 주소는 미리 입력 | 새 자산 ID와 이름. 인증 정보를 새로 선택. OS 감지·최근 연결·시작 명령·터널은 새로 설정 |
| 연결 취소           | 변경 이유나 새 지문을 확인하지 못함     | 모든 저장 정보                                        | 이번 연결 시도만 종료                                                                  |

신규 자산의 이름은 사용자가 입력한다. 이전 인증 정보나 그룹의 인증 기본값으로 자동 로그인하지 않는다. 그룹·태그를 이어받게 하더라도 인증과 시작 명령·터널을 자동 상속하지 않도록 명시적인 확인이 필요하다. 이전 자산은 기록 조회가 가능하게 보관하되, 재사용된 주소로 접속하는 활성 자산은 새 자산으로 정한다. 기존 자산에 실제 별도 주소가 있다면 그 주소를 수정한 뒤 다시 활성화한다.

‘키 교체’는 자산 정보를 보존한다는 뜻이다. 복구 연결 자체에서 시작 명령이나 터널을 자동 실행한다는 뜻은 아니다. 인증 완료 뒤 터미널을 열고, 자동 실행 기능은 별도의 기존 정책에 따라 처리한다.

## 키 종류가 바뀐 경우

RSA 지문과 ECDSA 지문이 다르다는 이유만으로 서버가 교체됐다고 판단하면 안 된다. 한 서버는 알고리즘별 호스트 키를 여러 개 가질 수 있다. 호스트 키는 서버의 정체성을 확인하는 키이며 사용자의 로그인 키와도 다르다. [NIST 호스트 키 정의](https://csrc.nist.gov/glossary/term/host_key)

판단을 세 가지로 나눈다.

1. **같은 종류의 키가 변경됨:** 교체 / 신규 자산 / 취소 화면.
2. **아직 등록하지 않은 다른 종류의 키:** ‘다른 종류의 호스트 키’라고 표시하고, 확인 후 기존 자산에 키 추가 / 취소. 이전 종류의 키는 보존한다. 새 키라는 사실 자체가 신뢰 근거는 아니다.
3. **처음 보는 서버:** 기존 첫 연결 설정을 따른다. 확인을 켰으면 앱 내부 등록 화면, 껐으면 첫 키 자동 등록. 이후 변경을 자동 승인하지 않는다.

기존 데이터에 키 종류가 없으면 비교 유형을 ‘알 수 없음’으로 표시한다. 임의로 RSA/ECDSA를 추측하거나 새 종류의 키라고 자동 승인하지 않는다.

## Passport에서 먼저 해결할 구조

현재 `src/main/store.ts`의 `known_hosts`는 `(address, port)`마다 지문 하나를 저장한다. `src/main/ssh.ts`는 다른 지문을 즉시 거절하고, `src/main/index.ts`의 네이티브 확인창은 첫 키 등록에만 사용한다. 따라서 버튼만 추가하면 신규 자산을 만들어도 같은 주소의 키가 덮어써지고, 자산별 이력 분리가 되지 않는다.

실제 구현에서는 다음을 함께 바꾼다.

- 자산 ID와 별도로 서버 정체성 ID를 둔다. 같은 서버를 여러 사용자·SSH/SFTP 설정으로 등록한 자산은 같은 정체성에 연결한다. 주소 재사용 시 새 정체성을 만들고 이전 정체성을 이력으로 보관한다.
- 키 저장은 서버 정체성·실제 접속 주소/포트·키 종류를 기준으로 분리하고, 키의 원문·지문·등록 시각·교체 이력을 보관한다. 다른 키 종류를 덮어쓰지 않는다.
- 기존 주소/포트 기반 기록은 소실 없이 이전하고 키 종류 미상 상태를 유지한다. 여러 자산이 같은 주소를 쓰면 같은 정체성으로 묶되, 변경 순간에는 영향을 받는 자산과 연결 기능을 표시한다.
- 메인은 제한된 유효기간의 확인 요청을 만들고 렌더러에는 자산·주소·키 종류·지문·선택지만 전달한다. 비밀번호나 개인키를 화면 이벤트에 넣지 않는다.
- 승인 결과는 해당 요청의 서버 키와 저장된 이전 버전에만 적용한다. 다른 창에서 이미 키를 바꿨거나 재접속에서 다른 키를 받으면 다시 확인한다.
- 신규 자산 생성·이전 자산의 이력 보관·키 등록을 하나의 트랜잭션으로 처리한다. 취소나 실패로 중간 상태가 남지 않아야 한다.
- 동시 SSH·SFTP·터널 시도는 같은 서버의 확인 요청을 묶는다. 취소·창 닫기·시간 초과에는 모두 종료한다. 새 자산으로 바꿀 때 기존 시작 명령과 터널을 그대로 재개하지 않는다.

현재 SSH 지문 불일치를 문자열 오류로 전달하는 부분은 구조화된 상태로 바꾸어야 한다. 호스트 키 변경은 일반 오류 토스트 대신 이 화면에 연결하고, 알고리즘 협상 오류는 별도의 복구 안내로 구분한다.

## CentOS 오류와 키체인 창의 관계

CentOS 5/6의 `no matching key exchange algorithm`은 호스트 키 확인보다 앞선 협상 실패다. 지문 교체로 해결되는 문제가 아니다. 벤치마크 이후 0.3.3에서 구형 방식도 항상 지원하도록 변경했으므로 호환 설정으로 이동하는 동작은 필요하지 않다. 남은 협상 실패는 서버 SSH 설정을 확인하도록 별도로 안내하고, 지문 확인은 그대로 수행한다.

macOS의 ‘Passport Safe Storage’ 접근 창은 OS 키체인 창이다. SSH 연결 화면으로 옮길 수 없다. 이 벤치마크는 앱이 표시하는 SSH 서버 지문 확인·변경 안내에 해당한다.

## 시안과 검증 범위

시안에는 키 변경, 첫 연결, 다른 종류의 키 세 가지 상황이 있다. ‘교체’와 ‘신규 자산’ 선택에 따라 다음 버튼과 설명이 달라지고, 신규 자산은 이름 입력 후 인증 선택 단계로 안내한다. 지문 확인 체크와 선택이 완료되기 전에는 진행 버튼이 비활성화된다. Esc는 취소한다. 어떤 선택도 실제 서버·DB에 접근하지 않는다.

로컬 Chromium에서 선택·확인·이름 입력 조건, 교체/신규/다른 종류의 키 분기, 취소·재설정, 390px 화면에서 가로 넘침 없음, 외부 네트워크 요청 0건, JavaScript 오류 0건을 확인했다. [검증 기록](benchmarks/ssh-host-key-preview.json), [화면 캡처](../design/ssh-host-key-preview.png). 이 검증은 시안의 동작 범위이며 실제 SSH 복구 기능의 구현 검증이 아니다. 운영 코드와 기존 0.3.2 설치 파일은 이번 벤치마크로 변경하지 않는다.

실제 구현 시에는 인증 전 차단, 첫 등록 설정과 변경 확인의 분리, 다중 키 보존, 동시 창에서 중복 승인 방지, 신규 자산의 인증·자동 실행 미상속, 이전 로그 소속 보존, 취소 시 저장 변경 없음, SSH/SFTP/터널 공통 처리까지 검증해야 한다.
